# eqp_workload_fastview 説明資料

- 対応スクリプト: `scripts/trial_factory/eqp_workload_fastview.py`
- 作成日 / 更新日: 2026-09-01

## 処理概要

`proc_history`（ロット×工程×設備の工程実績履歴）を対象に、設備ごとの
処理数・ロット待機時間を集計し、負荷の高い設備をパレート図で示す。
`eqp_workload_analysis`（旧版）の⑥-2・⑥-3を、⑥-2は全期間・日次、
⑥-3は選択日1日分・複数設備のガントへ拡張した別ツール（旧版は変更して
いない）。全期間分の日別データ（ガント区間・仕掛数量推移・ロット明細）
をあらかじめ`data/days/<日付>.json`として生成しておき、ローカル静的
サーバー（高速モード）で配信することで、日付を切り替えても表示中の
1日分だけを取得する構成にしている。

| ステップ | 一般的な呼称 | モジュール | このスクリプトでの内容 |
| --- | --- | --- | --- |
| ① 前準備 | EDA（探索的データ分析） | `prepare.py` | `profile_from_parquet()`で件数・欠損率・カテゴリ分布などを確認 |
| ② データ加工 | データクレンジング/前処理 | `process.py` | 必須列の欠損除去・型整形、`wait_minutes`/`next_eqp_id`/`prev_eqp_id`の付与 |
| ③ 分析 | 分析・モデリング | `analyze.py` | 設備ごとの処理数・待機時間集計、パレート、全期間の日次インデックス、選択日1日分のガント区間・サブレーン割当・仕掛数量推移・ロット明細抽出 |
| ④ 可視化 | 可視化・レポーティング | `visualize.py` | ①〜⑤・⑥-1〜⑥-4を1枚のシェルHTML＋日別JSONに組み立て。⑥-3/⑥-4のブラウザ側描画ロジックは`fast_client.py`が担う |

`process.py`・①〜⑤/⑥-1の集計ロジックは`eqp_workload_analysis`（旧版）
と同じ内容だが、旧版ファイルには一切手を入れない方針のため複製実装
している。

## I/O説明

### 入力

| 項目 | 内容 |
| --- | --- |
| `--input` | `proc_history`のParquetファイルパス（既定: `data/trial_factory/proc_history.parquet`） |
| 必須カラム | `lot_id`/`prodspec_id`/`mainpd_id`/`ope_no`/`ope_seq`/`eqp_id`/`start_time`/`end_time` |
| 前提条件 | `generate_proc_history`（`docs/reference/`）等で生成したサンプルデータを想定 |

### 出力

| 項目 | 内容 |
| --- | --- |
| `--output-dir` | 出力ルートディレクトリ（既定: `output`）。この配下の`trial_factory/<実行日>/`にレポートディレクトリ・プロファイルを書き出す |
| レポート（既定・`--serve`時） | `<実行日>/eqp_workload_fastview_<実行時刻>/`ディレクトリ一式。`index.html`（シェル）＋`data/daily_index.json`（⑥-2用の全期間日次集計）＋`data/days/<日付>.json`（⑥-3/⑥-4用の日別データ）で構成する |
| レポート（`--single-file`時） | 同ディレクトリの`index.html`のみ（`data/days/`は書き出さない）。初期表示日（稼働が最も多い日）1日分の⑥-3/⑥-4データだけを`index.html`に静的埋め込みし、`file://`で直接開ける自己完結HTMLにする。他日への切替はできない旨をレポート上部に注記する |
| プロファイル | `<実行日>/eqp_workload_fastview_profile_<実行時刻>.json`（`DatasetProfile`形式） |
| レポートの内容 | ①設備ごとの処理数、②③待機時間（合計・平均）、④⑤処理数×待機時間の散布図（①〜⑤は初期状態で折り畳み）、⑥-1パレート図（設備別待機時間合計、上位N台、非クリック・初期状態で展開）、⑥-2日別稼働率・処理数（全期間・日次、日クリックで⑥-3の対象日を切替）、⑥-3選択日1日分の複数設備ガント＋全仕掛数量推移。ガントは設備ごとに稼働中(Processing)／待機中(Waiting)を背景色で示し（1台でも着工していれば稼働中）、区間バー（Canvas描画、同一設備内の重複はサブレーン分割、ホバーは装置ID・開始・終了のみ）はその上に重ねて描く。マウスホイールでズーム・ドラッグでパン・ダブルクリックで全期間表示へリセットできる。仕掛数量推移グラフ（着工中／待機中の2分類積み上げ、Y軸に0・中間値・最大値の目盛あり）も同じ表示範囲に連動する（縦軸のスケールは1日全体の最大値で固定）、⑥-4選択ロットのグループ内工程明細 |
| 副作用 | `--output-dir`配下に新規ディレクトリ・ファイルを書き出す（同名上書きはしない。実行時刻がディレクトリ名に入るため）。`output/trial_factory/index.html`に実行結果を追記登録する |

## 実行オプション

```bash
# レポート生成のみ
uv run python scripts/trial_factory/eqp_workload_fastview.py \
  --input data/trial_factory/proc_history.parquet --output-dir output

# レポート生成後、高速モード（ローカル静的サーバー）で即座に開く
uv run python scripts/trial_factory/eqp_workload_fastview.py \
  --input data/trial_factory/proc_history.parquet --output-dir output --serve

# file://で開ける単一HTML版（初期表示日のみ、サーバー起動不要）
uv run python scripts/trial_factory/eqp_workload_fastview.py \
  --input data/trial_factory/proc_history.parquet --output-dir output --single-file
```

| オプション | 既定値 | 説明 |
| --- | --- | --- |
| `--input` | `data/trial_factory/proc_history.parquet` | `proc_history`のParquetファイルパス |
| `--output-dir` | `output` | 出力ルートディレクトリ |
| `--top-n` | `15` | パレート図・⑥-2〜⑥-4の対象にする上位設備数（待機時間合計の多い順） |
| `--period-days` | `0`（全期間） | ⑥-2の対象期間（日数、入力データの最初の日から）。既定の`0`は全期間を対象にする |
| `--serve` | 無効 | レポート生成後、ローカル静的サーバー（`http.server.ThreadingHTTPServer`、空きポート自動選択）で即座に配信する（高速モード）。生成済みの出力を配信するのみで、サーバー側での再集計は行わない |
| `--single-file` | 無効 | 日別データを別ファイルへ分割せず、初期表示日のみ埋め込んだ単一HTMLを出力する（サーバー起動不要。⑥-3/⑥-4は他日へ切替不可） |

高速モードは`docs/product-requirements.md`の「可視化レポートは`file://`
で開ける自己完結HTMLであること」という原則に対する、本ツール限定の
例外として認めている（詳細は同ファイル・`docs/architecture.md`参照）。

## 既知の制約・注意点

- 対象は実データではなく、`generate_proc_history`（`docs/reference/`）で
  生成したサンプルデータを前提とする。
- サンプルデータは設備の同時使用制約（1台1ロット）を持たないため、
  ⑥-3ガントチャートのサブレーン数が実際の工場のバッチ挙動より多く出る
  ことがある（レポート上部に注記を表示する）。
- ⑥-3・⑥-4は、ガント区間内・ホバーに`lot_id`を表示しない（ホバーは
  装置ID・開始・終了のみ）。`lot_id`は⑥-4の明細表クリック後にのみ表示
  する。
- ⑥-1パレート図は非クリックの静的表示（対象設備群は常に上位N台のため、
  1台に絞り込む役割が無い）。クリックで該当設備の⑥-3行へスクロールする
  等の代替導線は今回のスコープに含めていない。
- ①〜⑤・⑥-1・⑥-2は`common/charts/*`（Plotly）で描画し、⑥-3は
  ブラウザの`<canvas>`要素（`fast_client.py`が生成するJS、Canvas 2D
  API）で描画する。⑥-3・⑥-4は日別JSON（`data/days/<日付>.json`）を
  日クリックのたびに`fetch()`する構成のため、`--single-file`出力
  （`data/days/`を書き出さない）を`file://`で開いた場合は初期表示日
  以外への切替ができない。
- ⑥-3のズーム（マウスホイール）・パン（ドラッグ）は、表示幅30分〜1日
  （初期値）の範囲でのみ動作する。日を切り替える（⑥-2の別日クリック）
  たびにズーム・パン状態は初期化され、全期間表示（00:00〜24:00）に
  戻る。仕掛数量推移グラフもガントと同じ表示範囲に連動する（縦軸の
  スケールは1日全体の最大値で固定し、ズームしても伸縮しない）。WIPは
  15分刻みで集計済みのデータのため、最小表示幅（30分）付近までズーム
  すると折れ線が数点しかなく直線的に見える点に注意。
- ⑥-3ガントの装置ステータス背景（稼働中/待機中）は設備単位の判定で、
  同一設備の複数サブレーンのうち1本でも着工していれば稼働中とする
  （サブレーン単位の色分けではない）。将来的に「停止(Stop)」ステータス
  を追加する構想があるが、`proc_history`に停止理由・ダウンタイム情報が
  無いため現時点では未実装。
- 仕掛数量推移は「着工中／待機中」の2分類積み上げ（待機中は、対象設備群
  への着工待ちと、対象設備群を出て対象設備群の外へ向かう退出待ちを
  合算したもの。対象設備群内での移動待機を両方でカウントする二重計上は
  発生しない）。
- 性能実測（開発サンドボックス環境、`proc_history_sample.parquet`
  3,508,309行・設備400台）: 日付切替2回目以降・ロット選択→⑥-4更新は
  中央値10ms前後・95パーセンタイル40ms程度（目標100ms以内を達成）、
  初回の日付選択（`fetch()`含む）は95パーセンタイル30ms程度（目標
  300ms以内を達成）。高速モード初回起動（URLアクセス→⑥-2操作可能）は
  中央値2.2秒・95パーセンタイル2.8秒で目標2秒を上回った。原因は
  ①〜⑤・⑥-1・⑥-2が使うPlotly本体のCDN読込・JS解析コストであり
  （旧版`eqp_workload_analysis`と共通の依存）、fastview固有の処理は
  60〜90ms程度に留まる。代表的な開発PCでの再計測、および恒常的に
  未達の場合のPlotly依存見直しは今回のスコープ外とし、申し送り事項に
  記録した（`.steering/20260901-eqp-workload-fastview/tasklist.md`
  参照）。
