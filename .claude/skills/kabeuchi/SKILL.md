# 壁打ち（/kabeuchi）

目的は、**後続のAIレビューとテストが合否を判断できる requirements.md** を作ること。
アイデアを褒めることでも、実装方法を決めることでもない。

手順の位置づけは `docs/development-process.md` の「3. requirements.md の作成と承認①」を参照。

## 進め方の原則（GStack /office-hours から借りたもの）

- **1問ずつ聞く。** 複数の質問をまとめて投げない（AskUserQuestion が使えるならそれを使う。
  選択肢が作れない自由回答の質問は、文章で1問だけ聞いて返答を待つ）。
- **具体性だけが通貨。** 抽象的な回答（「使いやすく」「いい感じに」「必要に応じて」）は
  そのまま受け取らず、具体例を求めて同じ段階に留まる。
  例：「使いやすく」→「直近で使いにくかった操作を1つ挙げてください。何をしようとして、どこで詰まりましたか？」
- **言い換えて確認する。** 各段階の終わりに、聞いた内容を1〜3行で言い換え、合っているか確かめてから次へ進む。
- **立場を取る。** 「いろいろな考え方がありますね」で済ませない。前提や制約が怪しければ、
  怪しいと言い、何が分かれば判断が変わるかを示す。
- **深追いしすぎない。** 1段階で同じ論点を3回聞いても具体化しなければ、「（仮定）」と書いて先へ進む。

## 質問の順番

| 段階 | 聞くこと | 次へ進んでよい状態 |
| --- | --- | --- |
| 1. 痛みの具体例 | 最近実際に困った場面。どのデータ（ファイル・テーブル）で、何をしようとして、何が起きたか。それが月に何回あり、どれくらい時間を取られているか | 実在する場面が1つ以上、データ名つきで語られた |
| 2. 前提 | 入力データの形式・規模（行数・列）・列の型、利用者（誰が結果を見るか）、既存ツール（`src/`・`scripts/`・`docs/reference/`）との関係 | 入力と出力の形がそれぞれ1文で言える |
| 3. 制約 | 使えないもの（新しい依存・外部サービス）、性能（何秒以内・何行まで）、出力形式（HTML・CSV・Parquet）、期限 | 守るべき制約が列挙され、無いものは「無し」と確認できた |
| 4. 代替案 | 作らない場合はどうするか（Excel・既存ツールの流用など）。他の方法と比べて、あえて作る理由 | 作る理由が1文で言える（言えなければ、作らない選択肢も提示する） |
| 5. 成功基準 | **入力と期待値の組**を最低3つ（正常系1つ以上、境界・異常系1つ以上）。エラー時にどうなるべきか | 下の「データ関数のチェック」と合わせ、レビュー可能性チェック (a)〜(d) が○になる |

### データ関数のチェック（段階5で、データを扱う場合は必ず1つずつ聞く）

| ケース | 聞き方の例 |
| --- | --- |
| 欠損（NaN/None/空文字） | 「金額が空の行は、0として数えますか、除外しますか、エラーにしますか？」 |
| 0や負の値 | 「数量が0や−1の行はどう扱いますか？（返品などで実際にありえますか？）」 |
| 重複 | 「同じキーの行が2回あったら、合算・先勝ち・エラーのどれですか？」 |
| カテゴリ型 | 「カテゴリの表示順は決まっていますか？データに無いカテゴリも0として出しますか？」 |
| 文字列の数値 | 「"1,000" や "１０" のような文字列の数値は来ますか？来たら数値に直しますか？」 |
| 空データ | 「対象が0行のとき、空のレポートを出しますか、エラーにしますか？」 |

### 可視化を含む場合（段階5の後）

- どのグラフを何枚、どの順で置きたいか、どこを操作すると何が起きるかを聞く。
- ラフの画面イメージを作って見せる（`.steering/<作業>/mock-*.html` のモックHTML、またはASCII）。
  「全期間・全件を初期表示すると読めるか」もここで一度確認する。

## 「残りはおまかせ」と言われたら

推定で埋めてよい。ただし、推定した箇所すべてに「（仮定）」を付け、
requirements.md の該当箇所と、承認①の依頼文の両方で目立つようにする。

## 出力

1. `.steering/[YYYYMMDD]-[開発タイトル]/requirements.md` を、`docs/development-process.md` の
   「作業単位ドキュメントの記載内容 > requirements.md」の見出し構成で生成する。
   - 段階1の痛みは「背景」、段階2〜3は「変更・追加する機能の説明」「制約事項」、
     段階4は「背景」の末尾（作る理由）、段階5は「受け入れ条件」（入力と期待値の表）に入れる。
2. 末尾の「レビュー可能性チェック」の表を埋める。×があれば、該当する段階に戻って質問を続ける。
3. ○が揃ったら呼び出し元（steering-workflow）に戻り、要件の独立確認へ進む。
