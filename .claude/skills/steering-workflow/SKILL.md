# 機能追加・修正時のステアリングワークフロー

このSkillは、`docs/development-process.md`に定義された「機能追加・修正時の手順」を、
毎回確実になぞらせるためのものです。手順そのものの正本は`development-process.md`にあり、
このSkillはそれを実行する際のガイド役に徹します。内容を勝手に省略・簡略化しないでください。

## なぜこの手順が必要か

このリポジトリでは、実装に着手する前に「何を」「どう変える」を作業単位ドキュメントとして
先に言語化し、ユーザーの承認を得ることをルールにしています。理由は、後から手戻りが起きやすい
判断（要求の解釈、設計方針）を、コードを書き始める前に確定させるためです。承認を飛ばして
実装を進めると、要求と実装がずれたまま作業が進んでしまうリスクがあるため、必ず段階を踏みます。

## 手順

### 1. 影響分析

- 今回の変更が `docs/` 配下の永続的ドキュメント（product-requirements.md,
  functional-design.md, architecture.md, repository-structure.md,
  development-guidelines.md, diagram-guidelines.md, glossary/ など）の内容に
  影響するかを確認する。
- 基本設計そのものに影響する変更であれば、後述のステップ4で該当ドキュメントを更新する
  ことを前提に進める。

### 2. ステアリングディレクトリの作成

```bash
mkdir -p .steering/[YYYYMMDD]-[開発タイトル]
```

- `YYYYMMDD` は作業着手日、`開発タイトル`は内容が一目でわかる英語のkebab-caseまたは
  snake_caseにする（例: `.steering/20250115-add-tag-feature/`）。
- ディレクトリ名だけで「いつ・何をした作業か」が判別できることが目的なので、
  日付とタイトルのどちらも省略しない。

### 3. 作業単位ドキュメントの作成（1ファイルごとに承認を得る）

以下の3ファイルを、**この順番で1ファイルずつ**作成する。1ファイル作成したら、
必ずユーザーに内容を確認してもらい、承認を得てから次のファイルに進む。
承認前に複数ファイルをまとめて作らないこと（先に述べた通り、後戻りコストを
抑えるための手順なので、ここを省略すると本来の目的が達成できない）。

1. **requirements.md** — 変更・追加する機能の説明、ユーザーストーリー、
   受け入れ条件、制約事項
2. **design.md** — 実装アプローチ、変更するコンポーネント、データ構造の変更、
   影響範囲の分析
3. **tasklist.md** — 具体的な実装タスク、進捗状況、完了条件

### 可視化（グラフ・レポート画面）を含む場合の追加ルール

文章だけでは画面の出来上がりが共有できず、実装後に「思っていたものと違う」
「グラフが密集していて読めない」が判明して手戻りになる。そのため、可視化を
含む作業では次を必須とする（正本は`docs/development-process.md`）。

- **requirements.md にラフな画面イメージを載せる** — どのグラフを何枚、
  どんな順で置きたいか、どこを操作すると何が起きるか。手描き相当のラフでよい。
- **design.md に確定版の画面配置と各グラフの見せ方を載せる** — グラフの
  並び順・段組み、グラフ種類、縦横軸、色分けの意味、初期表示の範囲、凡例・
  ホバーの内容。`requirements.md`のラフを、データ量・描画性能・HTMLサイズ
  といった技術的制約を踏まえて確定させる。
  **「全期間・全件を初期表示して読めるか」は必ず検討する。**
- **実装に入る前に、画面イメージを見た状態で承認を得る** — 文章だけで承認を
  取らない。静的なモックHTMLやダミーデータで描いたグラフなど、実際に目で
  見られる形にして確認してもらう。

### 4. 永続的ドキュメントの更新（必要な場合のみ）

ステップ1で「基本設計に影響する」と判断した場合のみ、該当する`docs/`配下の
ファイルを更新する。影響がなければこのステップはスキップしてよい。

### 5. 実装開始

`tasklist.md`に基づいて実装を進める。コーディング規約・命名規則・スタイリング規約は
`docs/development-guidelines.md`を参照する（このSkillでは規約の詳細を繰り返さない）。

### 6. 品質チェック

実装が完了したら、以下を実行して問題がないことを確認する。

```bash
uv run ruff check .
uv run ruff format .
uv run mypy .
uv run pytest
```

`pytest`はユニットテストに加え、必要に応じて結合テストも実行する（対象がファイルI/Oや
DuckDB/Parquetを介した処理であれば、`tests/`配下に結合的な検証も書く）。

最後に、実装した内容が`requirements.md`の受け入れ条件を満たしているかを見直す。

## 注意事項

- 永続的ドキュメント（`docs/`）と作業単位ドキュメント（`.steering/`）を混同しない。
  前者はプロジェクト全体の恒久的な方針、後者は今回の作業限定の一時的な記録。
- Gitのブランチ運用（GitFlowの`feature/`ブランチなど）は
  `docs/development-guidelines.md`のGit規約を参照する。
