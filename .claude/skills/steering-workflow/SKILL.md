# 機能追加・修正時のステアリングワークフロー

## まず読むもの

**手順の正本は `docs/development-process.md`。着手前に次の2セクションを読み、
そのとおりに進めること。**

- 「機能追加・修正時の手順」（ステップ1〜6）
- 「作業単位ドキュメントの記載内容」（各ファイルに何を書くか）

このSkillは手順を再掲しない。両方に同じことを書くと必ず片方が古くなり、
どちらが正しいのか分からなくなるため。ここに書くのは
**「なぜ省略してはいけないか」と「実際に飛ばされやすい箇所」だけ**。

## なぜ省略してはいけないか

実装に着手する前に「何を」「どう変える」を作業単位ドキュメントとして先に
言語化し、承認を得る——これは形式のためのルールではない。要求の解釈や設計方針
といった**後から覆ると手戻りが大きい判断を、コードを書く前に確定させる**ための
手順である。承認を飛ばすと、要求と実装がずれたまま作業が進む。

急いでいるとき、あるいは「小さい変更だから」と思えるときほど飛ばしたくなるが、
そこで飛ばした結果の作り直しのほうが高くつく。内容を勝手に省略・簡略化しない。

## 飛ばされやすい箇所（正本の該当ステップを必ず確認する）

- **1ファイルごとの承認** — requirements.md / design.md / tasklist.md を
  まとめて作らない。1つ作るごとに確認を取り、承認を得てから次に進む。
- **可視化を含む場合の画面イメージ承認** — グラフやレポート画面を作るなら、
  requirements.md と design.md の承認を**文章だけで取らない**。目で見られる形
  （モックHTML、ダミーデータのグラフ等）を添えて承認を得る。
  承認ステップが増えるわけではなく、既存の承認に絵を添えるということ。
- **影響分析と永続的ドキュメントの更新** — 基本設計に影響するなら、
  実装後に `docs/` 側の記載も更新する（ステップ1で判断し、ステップ4で反映）。
- **対象外の判断** — 既存コードの質問・説明のみ、`docs/` の恒久ドキュメント
  だけの更新、初回セットアップは、このSkillの対象外。無理に適用しない。
