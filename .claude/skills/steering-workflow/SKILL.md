# 機能追加・修正時のステアリングワークフロー

## まず読むもの

**手順の正本は `docs/development-process.md`。着手前に次の2セクションを読み、
そのとおりに進めること。**

- 「機能追加・修正時の手順」（全体の流れ、ステップ1〜10、独立レビューの進め方）
- 「作業単位ドキュメントの記載内容」（各ファイルに何を書くか）

このSkillは手順を再掲しない。両方に同じことを書くと必ず片方が古くなり、
どちらが正しいのか分からなくなるため。ここに書くのは
**「なぜ省略してはいけないか」と「実際に飛ばされやすい箇所」だけ**。

## なぜ省略してはいけないか

人間の承認を requirements.md（可視化ありは design.md も）に絞ったのは、
それ以外の品質を **独立した目（文脈を持たないサブエージェント）と、先に書いたテスト**
で担保する前提があるから。独立確認・独立レビュー・テストの分離を飛ばすと、
誰も確認していない成果物が人間の承認なしに進んでしまう。承認を減らした分、
これらの工程は省略できない。

急いでいるとき、あるいは「小さい変更だから」と思えるときほど飛ばしたくなるが、
そこで飛ばした結果の作り直しのほうが高くつく。内容を勝手に省略・簡略化しない。

## 飛ばされやすい箇所（正本の該当ステップを必ず確認する）

- **壁打ちの判定** — 一文で言い切れない依頼、可視化を含む依頼は `/kabeuchi` で
  壁打ちしてから requirements.md を書く。省略してよい小さな修正でも、
  受け入れ条件の具体例（入力と期待値の組）は書く。
- **レビュー可能性チェック** — requirements.md の末尾の表 (a)〜(d) を埋める。
  ×があるのに承認に回さない（壁打ちに戻る）。
- **要件の独立確認** — 人間に承認を頼む前に、サブエージェントに requirements.md
  だけを読ませて抜けを挙げさせ、反映してから承認に回す。
- **承認の位置** — 承認①の後は design.md・tasklist.md・実装を承認待ちせず進める。
  ただし可視化を含む場合は design.md の承認②（確定版の画面を添える）を飛ばさない。
  可視化を含む場合は、承認①にもラフの画面イメージを添える（文章だけで通さない）。
- **独立レビューに渡すもの** — 指示文（`prompts/`）と成果物だけを渡す。経緯の説明や
  会話の要約を足さない（足すと独立でなくなる）。往復は3回まで。超えたら止めて報告する。
- **テストは実装の前に、別の文脈で** — 受け入れテストは実装より先に、サブエージェントに
  書かせて単独でコミットする。実装中にテストを書き換えない。誤りだと思ったら理由を
  添えて報告し、テストを書いた側に直させる。同じ失敗を3回直しても通らなければ止める。
- **反例テスト** — 独立レビュー③は判定だけで終わらせず、反例テストを書いて実行させる。
- **画面の確認** — 可視化を含む場合は、生成した HTML を実際に開いて操作し確認する。
- **PR の対応表** — 受け入れ条件とテストの対応表を PR に書く。Ready for review は
  人間が対応表を確認してから押す（Claude が押さない）。
- **影響分析と永続的ドキュメントの更新** — 基本設計に影響するなら、
  実装後に `docs/` 側の記載も更新する（ステップ1で判断し、ステップ5で反映）。
- **対象外の判断** — 既存コードの質問・説明のみ、`docs/` の恒久ドキュメント
  だけの更新、初回セットアップは、このSkillの対象外。無理に適用しない。
